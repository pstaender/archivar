# archivar

Web app for archiving photos, scans, documents and PDFs: upload (incl. phone camera), edit images, OCR, stacks and folders.

## Stack

- Runtime/server: **Bun** (`Bun.serve` with route table, `bun:sqlite`). No Express, no Vite – Bun bundles `src/client/index.html` itself.
- Frontend: **React 19** + **react-router** as a data router (`createBrowserRouter(routes)` from `src/client/App.tsx`; needed for `useBlocker`). Folders are routes: `/folders/wichtig/2026`, built with `folderHref()` in `src/client/routes.ts`. Client tests render through `renderApp()` (`createMemoryRouter`, returns the `router`).
- Icons: **Keyline Icons** (`@iconify-json/keyline-icons`). Add an icon to `src/client/icons/index.tsx`; the `keyline()` macro inlines the SVG at bundle time, so never import the 7 MB icon JSON elsewhere.
- Font: **Inter** variable (`@fontsource-variable/inter`, Latin subsets declared in `styles/fonts.css`).
- Language: **TypeScript** everywhere (strict, `noUncheckedIndexedAccess`).
- Styling: plain modern CSS with custom properties (`src/client/styles/`). **No CSS framework, no SASS/SCSS.** Native nesting is fine.
- Images: **Jimp** assembled from its `@jimp/*` packages in `src/shared/image/jimp.ts` (the `jimp` meta package ships a broken browser build). The same pipeline (`src/shared/image/pipeline.ts`) renders the live preview in the browser and the final image on the server.
- OCR: **tesseract.js** on the server (`deu+eng` by default, language data cached in `data/tessdata`). Orientation detection (`OcrEngine.detectOrientation`) needs the legacy engine, so it runs in a second worker with `osd.traineddata`; results below confidence 2 are ignored.
- PDFs: **unpdf** (text extraction, page rendering via `@napi-rs/canvas`).
- Denoise: **OpenCV.js** (`@techstark/opencv-js`, ~11 MB). `src/shared/image/denoise.ts` uses `bilateralFilter` and, after B/W, `connectedComponentsWithStats` to drop isolated specks (marks near text are kept). The server loads it at startup (`src/server/opencv.ts`), the editor's preview worker loads it on demand with `importScripts` from `/vendor/opencv-<version>.js` (served gzipped by `src/server/vendor.ts`) – never import the package in client code. Never `await` the OpenCV module (it is a self-resolving thenable); use `initOpenCv()`. Server tests preload `test/opencv.ts`. The prebuilt OpenCV.js has no `fastNlMeansDenoising`.
- Optional image formats: **ImageMagick** CLI, detected at startup (`MagickConverter.detect()`); tests use `FakeImageConverter` (accepts `image/webp`).
- Vectorizer: TypeScript port of **VTracer** (visioncortex/vtracer with the parts of visioncortex and flo_curves it uses) in `src/vectorizer/vtracer/`, no WASM. Ported: binary and hierarchical color clustering, stacked compositing, polygon/spline outlines, SVG path output; not ported: mosaic/cutout, watershed, palettes, the curve simplification pass, transparency keying.
- Automatic dewarping: **UVDoc** exported to ONNX (`models/uvdoc.onnx`, not in git, create with `bun run setup:uvdoc`), run with **onnxruntime-node** in `src/server/services/dewarp.ts`. The model only predicts a 2×45×31 grid; `src/shared/image/unwarp.ts` ports UVDoc's `bilinear_unwarping` (interpolate + grid_sample, `align_corners=True`) so the browser preview uses the same grid. Without the model the feature is hidden (`/api/config`).

## Commands

```sh
bun install
bun run dev          # hot reload, http://localhost:3000
bun run start        # production
bun run test         # server + shared tests, then client tests
bun run test:server  # src/server + src/shared
bun run test:client  # src/client with happy-dom preload
bun run typecheck
bun run setup:uvdoc  # one-time: export UVDoc to models/uvdoc.onnx (needs uv + git)
```

Do not run a bare `bun test`: client tests need the happy-dom preload, server tests must run without it (happy-dom replaces `fetch`/`Request`).

## Layout

- `src/shared/` – code used by client and server: types (API DTOs), edit settings normalization, folder path helpers, image pipeline (perspective warp, OpenCV denoise).
- `src/server/` – `index.ts` (entry), `routes.ts` (REST API), `context.ts` (wiring + current user), `db/` (migrations + repositories), `services/` (archive logic, imaging, OCR queue, PDF), `storage.ts` (files under `data/files`).
- `src/vectorizer/` – self-contained sub-application (imports nothing from the app): types, settings and their automatic defaults, area normalization, the `VectorizerBackend` interface with the VTracer backend (`backend.ts`, swap `vectorizer` there for another backend), the Web Worker (`worker.ts`) with its client (`client.ts`), and `server/paint.ts` (rasterizes areas with `@napi-rs/canvas`). Its tests run with `test:server`.
- `src/client/` – `pages/`, `components/`, `editor/` (canvas preview, corner overlay, controls), `hooks/` (contexts for toasts, folders, uploads).
- `test/` – test helpers (`server.ts` starts an API server on a random port with in-memory SQLite and a fake OCR engine; `client.tsx` has fetch mocks and render helpers).

## Domain rules

- Multi-user data model (`user_id` on every table) but no login yet: `context.currentUser()` returns the `default` user, or the owner of a bearer token (`Authorization: Bearer arch_…`, table `api_tokens`, only the SHA-256 is stored; unknown tokens get 401). Tokens are managed in „Einstellungen“ → „API“ (`ApiTokens`, `/api/tokens`); `scripts/upload.sh` is the example client. Upload fields `ocr`/`ocrAllText` that are left out follow the user's settings (test servers turn `autoOcr` off). Keep every query scoped by user id.
- Folders are labels with hierarchical paths (`wichtig/2026`). Filtering by a folder includes its sub-folders. Documents and stacks can have many folders. The selection's „Ordner“ dialog (`FolderTargetDialog`) picks existing or new folders: „Hinzufügen“ adds them, „Verschieben“ (`moveToFolders`) removes the folder being viewed and its sub-folders first (in the overview: all folders). Inside a folder, the „Ordner“ button with the minus icon removes the selection from that folder and its sub-folders. The selection bar also has „Alle markieren“ and „Stapelverarbeitung“ (`BatchDialog`), which starts a batch job.
- A stack groups documents in order. Empty stacks are deleted automatically.
- „Smarte Stapel“ (library icon button `SmartStackIcon`, layers and a sparkle combined from two Keyline icons, kept in `localStorage` `archivar.smartStacks`, off in the custom order): `groupSmartStacks` (`src/client/smartStacks.ts`) groups documents in the view only – numbered series by name first (`seriesName`: the number at the end counts, numbers inside the prefix such as a scan time are ignored; gaps ≤ 3), then similar names (Levenshtein via **fastest-levenshtein**, `similarNames`: 80 % of short names down to 60 % from 30 characters, compared with the 8 neighbours in name order; names differing only in digits are left to the series rule), then chains of uploads each less than 2 minutes after the previous one – and shows them as `SmartStackCard` where their first document was. Opening one shows just its documents (`?smart=<ids>`); selecting one selects its documents, so „Stapeln“ turns it into a real stack. Nothing is stored.
- The library's card shape (Hochformat – default –, Querformat, Quadratisch; icon buttons next to the sort select) is kept per browser in `localStorage` `archivar.cardShape`, the same for the overview and all folders (`data-card-shape` on `.library`).
- Library sorting (`sortLibrary` in `archive.ts`, `?sort=`; the choice is kept per browser in `localStorage`, separately for folders – default `custom`, listed first – and the overview – default `updated`): `custom` only exists inside a folder – positions per folder in `folder_order` (by path, also for folders that only exist through sub-folders; items not arranged follow by upload date). The grid uses **@dnd-kit** (`SortableGrid`): mouse/touch drag the card, the keyboard only via the grip (Enter on the card link must still open it). dnd-kit stops the click after a drag on window but not the link's default action, so `SortableGrid` prevents it with its own native window listener.
- Edit settings are stored as JSON on the document and always pass through `normalizeEditSettings`. The original file is never modified; derived files (`preview-<size>.jpg`, `processed.jpg`, `thumbnail.jpg`) live in `data/files/derived/<id>/`.
- Pipeline order: rotate → dewarp grid → crop/perspective → denoise (smoothing) → levels/brightness/contrast → color → speck removal (B/W only, when denoise > 0).
- Grayscale „Kanäle“ (`grayMix`, `src/shared/image/grayMix.ts`) work like Photoshop's „Schwarzweiß“: one weight per hue (reds … magentas, -200..300 %). null is the plain luma conversion; the editor shows it as the weights `LUMA_GRAY_MIX` (equivalent in this model) and stores sliders moved back to them as null. Only used in grayscale mode, not for B/W. Denoise parameters scale with the image size so the preview matches the final render.
- The editor's base image (`/preview`) is at most `PREVIEW_SIZE` (3000 px, `src/shared/preview.ts`) and is filtered at that size, because threshold/contrast look different on a downscaled image. The size is part of its file name and URL, so changing it regenerates the file (on demand) and busts the browser cache; previews of other sizes are deleted at startup (`removeStalePreviews`). The live preview renders in Web Workers (`src/client/editor/preview.worker.ts` via `PreviewRenderer`, which runs one render at a time and drops superseded ones). Bun's HTML bundler does not bundle workers, so `src/server/vendor.ts` bundles it with `Bun.build` as a classic script at `/assets/preview-worker.js` (rebuilt per request in development, ETag + `no-cache`). `ImageEditor` uses a second worker with a 1200 px copy for drafts: when the last full render took over 250 ms, the draft shows while settings change and the full image once they settle. Browser entry points import `src/shared/bufferGlobal.ts` first (Jimp needs a global `Buffer`). Saturation/hue use `adjustColor` (`src/shared/image/color.ts`), a fast equivalent of Jimp's tinycolor-based `color()`.
- „Vektor“ tab (images only, first in the „Mehr“ menu; `VectorCanvas`/`VectorControls` in `src/client/editor/VectorEditor.tsx`, state in `useVectorAreas`): rectangles (0..1 of `/edited`) whose pixels are replaced by a vector graphic. Drawing an area asks the worker for suggested settings (`suggestVectorSettings`: B/W when the pixels are gray with few mid tones, Otsu threshold, less detail for many colors, more for small or low-resolution areas), then vectorizes it; moving, resizing or changing settings vectorizes it again (one request at a time, superseded ones are cancelled by replacing the worker). Settings: Schwarzweiß/Farben, Details 1–5, Schwelle (B/W), Glatt/Eckig; the backend scales speckle size with `pixelScale` (relative to A4 at 300 DPI, `regionPlan`; areas over `MAX_VECTORIZE_SIZE` are scaled down first). The worker loads the image itself (`fetch` + `createImageBitmap`, bundled by `vendor.ts` at `/assets/vectorizer-worker.js`). Areas are stored with their graphic (`{ width, height, background, paths: [{ d, fill }] }`, path data restricted to `M/L/C/Z` and numbers) in the table `document_vectors` (not in `documents`, as graphics can be MBs; the DTO only has `vectorCount`/`vectorsOutdated`, same geometry rule as shapes) via `GET/PUT /api/documents/:id/vectors`; areas without a graphic are dropped. `renderDerivatives` paints them onto `processed.jpg` before the shapes, `/edited` is the image without both, and a change re-queues OCR when the image had text. The PDF export draws them as vector paths (`src/vectorizer/server/pdf.ts`, coordinates unchanged) on top of `ImagingService.pdfImage` – the image with the areas filled with their background – and the shapes again on top; detailed graphics can be larger than the 300 DPI raster they replace. Not part of image presets.
- „Formen“ tab (images only, after „Vektor“ in the „Mehr“ menu; `ShapeCanvas`/`ShapeControls` in `src/client/editor/ShapeEditor.tsx`): filled rectangles (`src/shared/shapes.ts`, positions 0..1 relative to the edited image) drawn on `/edited` (the edited image without shapes, `derived/<id>/edited.jpg`, only kept while there are shapes). They are stored in `documents.shapes` (JSON with the `shapeGeometry` of the settings they were drawn on → `shapesOutdated` when rotation/crop/dewarp change later; they stay where they are) and saved with `PATCH { shapes }`, separately from the edit settings. `renderDerivatives` paints them onto `processed.jpg`, so thumbnail, OCR and PDF export include them; changed shapes re-queue OCR when the image had text, so blacked-out text leaves the text, search and PDF layer. The „Bearbeiten“ tab overlays them (the current draft) on its live preview and „Vorschau“ with CSS, except while corners are edited, as neither render paints them. Image presets can carry them as the step `shapes` (offered in both tabs' „Bildeinstellung speichern“; they replace the image's shapes on import, in batch jobs via `updateDocument`, and in the editor, where `apply-preset` returns them for the „Formen“ draft).
- A dewarp grid is stored in the edit settings together with the rotation it was predicted for; it is dropped when the rotation changes. Crop/perspective corners are normalized (0..1) relative to the rotated (and dewarped) image.
- Auto B/W (`src/shared/image/autoBw.ts`) analyses the image after geometry/denoise: brightness/contrast stretch the luma range, variants differ only in the threshold (Otsu first, then darker, then lighter). It keeps `autoLevels` (the analysis then starts from the normalized image, as the pipeline normalizes first). The client caches variants per geometry and auto levels and cycles through them on repeated clicks.
- Uploads store the file's SHA-256 (`documents.sha256`; files stored before are hashed at startup, `hashMissingFiles`). The upload response (`UploadedDocument`) lists the user's documents with the same content in `duplicates`: the file is stored anyway, the client warns and the import job item gets a note.
- Supported uploads are the Jimp image types and PDF (`src/shared/uploads.ts`, used for the file inputs' `accept` and to skip dropped files). If ImageMagick is installed (`magick`, or IM6 `convert`), HEIC/HEIF/AVIF/WebP/JPEG XL/JPEG 2000 are accepted too (`/api/config` → `convertibleImageTypes`): `src/server/services/magick.ts` converts them to PNG with an explicit coder prefix, the result is cached as `derived/<id>/source.png` and everything else (editor preview, OCR) works on that. The client uploads files one request at a time via `XMLHttpRequest` to show progress; client tests mock it with `mockXhr()`.
- „Auto-Zuschnitt“ (`src/shared/image/autoCrop.ts`, OpenCV) finds the largest four-cornered page outline (Canny edges or Otsu, like z80z80z80/autocrop) in the rotated and dewarped image; almost upright outlines snap to a plain crop, the client opens the matching corner mode so they can be adjusted. „Auto-Drehen“ sets the absolute rotation detected on the original (`POST /orientation`).
- User settings (`src/shared/settings.ts`, `users.settings` JSON, `GET/PATCH /api/settings`) are stored per user on the server and edited in the „Einstellungen“ dialog (sidebar) with the tabs „Bildgrößen“ and „Import“ (OCR switches, `importOcrLanguages`, `importPresetId`, `importFolders`; the upload route adds the import folders and passes the preset and languages). The client reads them through `SettingsProvider`/`useSettings` (the upload sends `ocr`, `ocrAllText` from them); OCR switches that older versions kept in `localStorage` are moved to the server once.
- Image presets („Bildeinstellungen“, `src/shared/presets.ts`, table `image_presets`, `/api/presets`) store only chosen steps: automatic ones (`autoRotate`, `autoDewarp`, `autoCrop`, `autoBw`) are worked out again per image, the rest are fixed values; settings left out stay unchanged. The editor offers the non-default settings as steps (`presetStepsFromSettings`; it remembers which values came from the auto tools; hand-drawn corners become the fixed step `crop`) and applies a preset via `POST /api/documents/:id/apply-preset` (on top of the draft, nothing saved). The page `/presets` („Bildeinstellungen“ in the sidebar, `PresetsPage`) lists them with their steps (`describeStep`) and marks the import preset, for editing and deleting; deleting the import preset clears `importPresetId`. Uploads get the import preset before rendering and OCR, whether OCR runs or not („Text nach dem Upload erkennen“ only switches OCR). Every user gets the preset „OCR Optimiert“ as import preset once (`seedImportPresets` at startup, `users.import_preset_seeded`); the old settings `uploadEnhancement`/`autoDewarp` are turned into an equivalent preset there. Test servers turn the import preset off unless `startTestServer({ importPreset: true })`.
- Languages: OCR runs with `ARCHIVAR_OCR_LANGS` (`/api/config` → `ocrLanguages`) unless the document has its own `ocrLanguages` (set via `POST /ocr` `{ languages }`, list in `src/shared/languages.ts`; `TesseractEngine` switches with `reinitialize`). The language of stored text (OCR, PDF text, edits) is detected with **franc** (`services/language.ts`, ≥ 20 characters) into `ocrLanguage`; texts without one are checked again at startup. Similar languages (Danish/Norwegian) can be confused. Uploads use the setting `importOcrLanguages`; when it is null („Automatisch“) they are queued with `detectLanguage`: if the text is in a supported language that is not a default one, `OcrQueue` recognizes it again in that language and keeps the more confident result (then also storing it as the document's `ocrLanguages`).
- OCR drops probable noise by default (`src/server/services/ocrFilter.ts`: low-confidence lines, lines without a real word, very unsure words) and stores the count in `ocr_removed`. `allText` (upload field `ocrAllText`, body of `POST /ocr`) keeps everything; the document remembers it (`ocrAllText`) so the text tab can offer „Unsichere Textteile ausblenden“ (a new run with the filter).
- OCR input is reduced to A4 at 300 DPI (`OCR_MAX_SIZE` 3508 px, `fitForOcr` in `imaging.ts`): in 600 DPI scans Tesseract splits lines and misreads most words. `ocr_layout` boxes are relative to that reduced image; the PDF export uses the full `processed.jpg` (`processedJpeg`).
- Jobs (`src/shared/jobs.ts`, tables `jobs`/`job_items`, `/api/jobs`, page `/jobs` „Stapelverarbeitung“ in the sidebar with the number of running jobs): batch jobs store a snapshot of the preset and the OCR options and run in the background in `JobQueue` (`services/jobs.ts`, one document at a time: preset on images via `applyPreset` + `updateDocument`, then `requestOcr` for images and PDFs; `resume()` at startup). Uploads create an import job with one item per file; each upload sends `jobItemId`, the client reports uploads that never arrived, and after a restart items still waiting are marked as interrupted. An item's `ocr` state is derived from its document's text recognition only until that run finishes: `setOcrResult` then settles the waiting items (`ocr_settled`, outcome stored as the item's status/error), so later runs from other jobs never change finished jobs (items and documents are n:m). Finished jobs show their duration (`finishedAt`: the latest item end – `job_items.finished_at`, or `ocr_finished_at` of settled items; null for jobs from before; `formatDuration`). The page shows times relative (`formatRelativeTime`: today „vor 5 Minuten“, then „Gestern“/weekday, after six days date and time). `JobsProvider` polls while a job is active (no time limit) and `useRefreshOnJobProgress` refreshes the library and stack pages.
- OCR runs asynchronously in `OcrQueue` (in memory only): at startup `resume()` re-queues documents left `pending`/`running` by a previous process, and each image/PDF page gets `OCR_PAGE_TIMEOUT_MS` (3 min) before the document fails with a German message and the Tesseract worker is replaced. Clients poll with `usePolling` (background `refresh()`, so `loading` does not flicker; gives up after 10 min).
- PDF export (`POST /pdf`, `src/server/services/searchablePdf.ts`, **pdf-lib**): one page with the edited image (`ImagingService.pdfImage`, long side 842 pt) in the body's `quality` (`PdfQuality`: `low` 150 DPI q65, `medium` 300 DPI q75, `high` up to 600 DPI q90, `original` full resolution re-rendered from the original without loss as PNG, or a custom 0–10 → JPEG q5–100 at 300 DPI; default: the setting `pdfImageQuality`, old values `150`/`300` are read as `low`/`medium`), scaled for A4 with `@napi-rs/canvas` in `pdfImage.ts`; B/W documents always become Flate-compressed 1-bit image XObjects written directly, since pdf-lib only embeds 8-bit images. Both „PDF“ buttons (`PdfButton`: „Datei“ tab, selection bar) download with the setting, their arrow opens a menu with the qualities and „Eigene …“ (slider, last value in `localStorage` `archivar.pdfCompression`) and the text as invisible Helvetica (render mode 3, horizontally scaled into each box; characters outside Windows-1252 lose accents or become „?“). OCR stores the kept lines' boxes normalized to 0..1 in `ocr_layout` (not in the DTO; `getOcrLayout`) together with the edit settings they were recognized for. The text is put on those boxes only if the settings are unchanged and the text has the same number of non-empty lines; otherwise lines are spread evenly over the page (only shrunk, never stretched). The „Datei“ tab exports it with the stored text (next to the original download). `POST /api/export/pdf` combines several documents (selection „PDF“, stacks expanded in order); uploaded PDFs are copied page by page with pdf-lib (422 if one cannot be read).
- Unsaved edit settings: `useLeaveGuard` (`src/client/hooks/leaveGuard.ts`) holds back route changes (`useBlocker`) and leaving the „Bearbeiten“ tab, and `UnsavedChangesDialog` offers Speichern/Verwerfen/Abbrechen; closing the browser tab only gets the browser's own `beforeunload` question. Call `skipNext()` before navigating away on purpose (e.g. after deleting).
- Saving edit settings renders `processed.jpg`/thumbnail on the server, so it runs in the background (`src/client/editSaves.ts`): the page takes the new settings at once, saves of a document run one after another, a toast reports the result (on failure the settings fall back), and OCR/PDF export wait for pending saves (`whenEditsSaved`). Library and stack pages refresh when a save finishes.
- While crop/perspective corners are shown (also after „Auto-Zuschnitt“), Enter applies them (`EditControls`, ignored in text fields).
- Document tabs (`TabBar`, `src/client/components/TabBar.tsx`): „Bearbeiten“ (images), „Text“ and „Datei“ (id `details`: downloads, folders, file details) are tabs, „Vektor“ and „Formen“ sit in the „Mehr“ menu, whose button then shows the open one's name; the tab list scrolls sideways when it does not fit. Client tests open tabs with `selectTab()` from `test/client.tsx`. The page opens on the tab chosen last (`localStorage` `archivar.documentTab`, for all documents; „Text“ by default). ← / → and the chevron buttons go to the previous/next document: inside a stack (`?stack=`) its pages, otherwise the documents of the library page last shown in this browser tab (`rememberDocumentOrder`, `sessionStorage`). `useArrowNavigation` leaves the keys to focused fields, sliders and open dialogs and ignores them with modifiers or when a handler already used them (crop handles, shapes). Images are shown with `ZoomableImage` (fit by default, zoom steps from `src/client/zoom.ts`, 100 %, open in new tab). In „Bearbeiten“, „Vorschau“ (`PreviewBar`, `useProcessedPreview`) renders the unsaved draft at full resolution via `POST /api/documents/:id/render` (nothing is stored) and shows it instead of the live canvas, with a 100 % `Magnifier` on mouse hover; any settings change drops it and aborts a running render.
- UI is German, monochrome (grays only). Colors only for error/warning/success via `--color-danger|warning|success`.

## Conventions

- Code, identifiers and commits in English. UI strings in German.
- No comments unless the reason for the code is not evident from the code itself.
- Prefer maintained npm packages over hand-written code; add new design tokens to `tokens.css` instead of hard-coding values.
- In client tests, assert absence inside `waitFor` with a boolean (`queryBy…(…) === null`): when a retried assertion fails, Bun prints the whole DOM element, which can take so long that the test hangs.
- Write tests for new behavior: API tests in `src/server/*.test.ts` via `startTestServer()`, component tests next to the component.
- Commit automatically when a piece of work is done and tests pass. **Never push.**
